# Invoice Calculation Engine & DAG Architecture Specifications

This document defines the mathematical invariants, topological sorting rules, formula encoding, and evaluation lifecycles governing the invoice engine in `@starter/api` (`apps/api/src/features/invoices/engine`).

---

## 1. Core Architecture & Single-Value Row Model

### Single-Value Row Evaluation
The invoice engine operates on a simplified single-value row architecture:
- Parent rows (`EvaluatorRow`) directly hold `valueType` (`normal` | `formula`), `formula`, and `initialValue` / `manualValue`.
- Sub-components are obsolete and completely bypassed in calculation.
- Evaluation paths:
  - `normal`: Row base resolves directly to `manualValue ?? initialValue ?? "0"`.
  - `formula`: Expression is evaluated against the current engine `scope`.

### Mathematical Precision (`mathjs`)
- All calculations use `mathjs` configured with `BigNumber` at **20 decimal digits of precision**.
- Currency outputs are formatted to fixed scale (6 decimal places internally, formatted to 2 decimal places for user display).
- No floating-point rounding errors (`0.1 + 0.2 === 0.300000`).

## 2. Token Namespace & Conventions

The engine maintains a strict, decoupled token taxonomy:

| Token Format | Represents | Source / Scope |
| :--- | :--- | :--- |
| `<ROW_TOKEN>` | Row Total (Base + Row Charges) | Generated by parent row |
| `<ROW_TOKEN>_BASE` | Row Base Value | Evaluated row value before charges |
| `<ROW_TOKEN>_CHARGES` | Row Charges Sum | Sum of all line charges on this row |
| `<CHARGE_TOKEN>` | Individual Row Charge | Charge line item value |
| `SEC_<SECTION_TOKEN>` | Section Total | Sum of all rows & section charges |
| `SEC_<SECTION_TOKEN>_BASE` | Section Base Sum | Sum of all row base values in section |
| `SEC_<SECTION_TOKEN>_CHARGES` | Section Charges Sum | Sum of all row & section charges in section |
| `<SEC_CHARGE_TOKEN>` | Individual Section Charge | Section-level charge value |
| `TPL_<CONSTANT>` | Template Constant | Defined per template |
| `GBL_<CONSTANT>` | Global Constant | System / Organization constant |
| `FILE_<FIELD>` | Project Custom Field | Stored in `projects.customFields` (e.g. `HOURS`, `RETAINER_RATE`) |
| `EXP_<CATEGORY>` | Expense Category Total | Real-time sum of project expenses matching category `tokenKey` |
| `EXP_TOTAL` | Total Project Expenses | Real-time sum of all recorded project expenses |
| `PERIOD_START` | Billing Period Start | Invoicing period start timestamp or boundary |
| `PERIOD_END` | Billing Period End | Invoicing period end timestamp or boundary |

## 2.1 AST Math Functions & Extensions (`ast-evaluator.service.ts`)

The evaluation engine natively supports the following financial and mathematical functions via `mathjs`:

| Function | Signature | Description |
| :--- | :--- | :--- |
| `CLAMP` | `CLAMP(value, min, max)` | Constrains `value` to lie between `min` and `max` (inclusive) |
| `MIN` | `MIN(a, b, ...)` | Returns the smallest value among the arguments |
| `MAX` | `MAX(a, b, ...)` | Returns the largest value among the arguments |
| `ROUND` | `ROUND(value, [decimals])` | Rounds to the specified number of decimal places (default: 0) |
| `FLOOR` | `FLOOR(value)` | Rounds down to the nearest integer |
| `CEIL` | `CEIL(value)` | Rounds up to the nearest integer |
| `ABS` | `ABS(value)` | Returns the absolute value |

### Period Scoping & Live Dynamic Sync
- When `periodStart` and `periodEnd` are `null`, the engine dynamically aggregates **all** recorded expenses for the project (`EXP_*`, `EXP_TOTAL`), ensuring live recalculation as new expenses are logged.
- When `periodStart` and `periodEnd` are provided, the engine scopes `EXP_*` and `EXP_TOTAL` strictly to expense entries matching `e.spentAt >= periodStart AND e.spentAt <= periodEnd`.

## 3. Formula Codec & Database Storage (`formula-codec.ts`)

To ensure template formulas remain resilient when tokens or rows are renamed, formula strings are stored with immutable UUID references.

### Storage Syntax
- **Row Tokens**: `{{$row:UUID}}`, `{{$row:UUID}}_BASE`, `{{$row:UUID}}_CHARGES`
- **Section Tokens**: `{{$sec:UUID}}`, `{{$sec:UUID}}_BASE`, `{{$sec:UUID}}_CHARGES`
- **Template Constants**: `{{$tpl:UUID}}`
- **External Tokens**: `FILE_*`, `GBL_*`, `CAT_*` remain plain text.

### Codec Lifecycle
1. **Encode on Save (`encodeFormula`)**:
   - Replaces user-facing token names with UUID tags.
   - Encodes longer suffixes first (`_BASE`, `_CHARGES`, `_TOTAL`) before bare tokens to prevent prefix collisions.
2. **Decode for Display / API (`decodeFormula`)**:
   - Replaces UUID tags with current human-readable token names before returning API responses to the web client.
3. **Decode for Evaluation (`decodeFormulaForEval`)**:
   - Decodes stored formulas into bare token names for AST execution.

## 4. Evaluation Sequence & Token Publication Order (`ast-evaluator.service.ts`)

The evaluation lifecycle follows a strict sequence to guarantee that dependent tokens and charges resolve without null/zero fallbacks:

```
[Topological Order across Sections & Rows]
   │
   ├── 1. Evaluate Row Base Value
   │      • normal  → manualValue ?? initialValue
   │      • formula → math.evaluate(decodedFormula, scope)
   │
   ├── 2. Publish Row Base Token into Scope
   │      • scope[<rowToken>_BASE] = baseValue
   │      • scope[<rowToken>]      = baseValue  <-- EXPOSED BEFORE CHARGES!
   │
   ├── 3. Evaluate Row Charges
   │      • Each charge formula evaluated against scope (references rowToken as base)
   │      • scope[<chargeToken>] = chargeValue
   │
   ├── 4. Publish Row Derived Values
   │      • chargesSum = SUM(row charges)
   │      • scope[<rowToken>_CHARGES] = chargesSum
   │      • scope[<rowToken>] = baseValue + chargesSum  (Updated to final Total)
   │
   ├── 5. Aggregate Section Values
   │      • SEC_X_BASE    = SUM(row base values in section)
   │      • SEC_X_CHARGES = SUM(row charge values in section)
   │      • SEC_X_TOTAL   = SEC_X_BASE + SEC_X_CHARGES
   │
   ├── 6. Evaluate Section Charges
   │      • Each section charge evaluated (references SEC_X_BASE or constants)
   │      • Added to section charges total
   │
   └── 7. Grand Total
          • INVOICE_TOTAL = SUM(SEC_X_TOTAL for all sections)
```

> [!IMPORTANT]
> **Base Token Priority**: The row base value **MUST** be published to `scope` before evaluating that row's charges. If charges evaluate before base registration, formulas like `PORT_DUES * 0.15` evaluate to `null` or `0`.

## 5. DAG Validation & Cycle Detection (`dag-validator.service.ts`)

Before any evaluation occurs, templates pass through `DagValidatorService.validate()`:

### Pass 1: Duplicate Token Detection
- Verifies that all row tokens, charge tokens, section charge tokens, and section names are unique.
- Fails immediately with `DUPLICATE_TOKEN` if collisions exist.

### Pass 2: Scope Constraint Enforcement
- **Row Charges**: May **ONLY** reference their parent row's base value (`<rowToken>_BASE`) or external constants (`FILE_*`, `GBL_*`, `TPL_*`).
  - Referencing sibling rows, other sections, or row total raises `CHARGE_SCOPE_VIOLATION`.
- **Section Charges**: May **ONLY** reference their parent section's base value (`SEC_<secToken>_BASE`) or external constants.
  - Referencing other sections or rows raises `CHARGE_SCOPE_VIOLATION`.
- **Section Scope Boundary**: Rows inside Section X cannot reference Section X totals or section charges.

### Pass 3: Kahn's Algorithm for Topological Sort
- Builds an in-degree map and directed graph of all token nodes.
- Enqueues nodes with `inDegree === 0`.
- If `topologicalOrder.length < totalNodes`, the remaining nodes form a cycle and the engine rejects evaluation with:
  ```json
  {
    "code": "CIRCULAR_DEPENDENCY",
    "message": "A circular dependency was detected involving these tokens: A, B, C"
  }
  ```

## 6. Error Taxonomy

| Error Code | HTTP Status | Trigger Condition |
| :--- | :--- | :--- |
| `CIRCULAR_DEPENDENCY` | `422` | Cycle detected in formula dependency graph |
| `CHARGE_SCOPE_VIOLATION` | `422` | Charge references illegal out-of-scope token |
| `DUPLICATE_TOKEN` | `422` | Same token name declared more than once |
| `INVALID_FORMULA_SYNTAX` | `422` | Unbalanced parentheses, trailing operators, malformed syntax |
| `UNRESOLVED_REFERENCE` | Warning / Notice | Token referenced in formula does not exist in template (zero-filled during preview) |
| `EVALUATION_FAILED` | `500` | MathJS evaluation threw a runtime arithmetic error (e.g. division by zero) |
| `REORDER_VIOLATION` | `422` | Moving a row to a new index creates an illegal forward/circular reference |
